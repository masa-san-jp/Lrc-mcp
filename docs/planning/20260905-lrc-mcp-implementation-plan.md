## 1. 進め方と正本

[設計仕様書](../design/20260905-lrc-mcp-design-specification.md)を要求・API・処理契約の正本、本書を実装順・完了条件・状態の正本とする。[README](../../README.md)は入口であり、技術仕様を独自に追加しない。タスクやIssueには本書のIDと該当仕様へのリンクを付ける。タスクの都合で制約や対象範囲を黙って変更しない。

この依頼で作成する成果物は3つのMarkdown文書である。下記のコード、試験、コマンド、CI、リリースはこれから実装するもの。本文中のパスは将来の配置予定であり、存在済みのファイルを意味しない。

実装担当は次の手順を繰り返す。

1. 依存タスクと対象要求IDを読む。着手可能なタスクを選び`in_progress`へ更新する。
2. 入力と期待結果を確認し、該当範囲を実装する。SDK固有の推測は検証ゲートへ送る。
3. タスクに割り当てた試験を実施する。失敗時は同じ仮説を無限に試さず、再現条件を記録して修正する。
4. 完了条件と証跡を確認し、コード・試験・仕様差分・状態更新を同じPRへまとめる。
5. 外部環境が必要なら`blocked_environment`、仕様判断が必要なら`blocked_decision`を記録し、独立した未完了タスクへ進む。

`done`は完了条件を満たし証跡がある場合のみ使用する。環境がない試験をモックに置き換えて実機完了にしない。失敗条件の再現・ログ採取・原因仮説の見直し後も解決しない場合は、未達条件と再開に必要な入力を明記して一旦終了する。

ライブラリの版固定、通常のファイル分割、確認済みSDKキーの対応づけなど、要求を変えない実装判断は担当エージェントが根拠を記録して進める。`blocked_decision`は、要求同士の矛盾や製品範囲の変更など、既存仕様から解決できない判断に限定する。

## 5. タスク詳細

### T-00：基盤

- 入力：仕様第2・5・15章。出力：Pythonパッケージ基盤、依存lock、最小CI、開発手順。配置：`pyproject.toml`、`uv.lock`、`src/lrc_mcp/`、`tests/`、`.github/workflows/`。
- 手順：公式MCP Python SDKの採用版を選び、Python/Luaの対応版を記録する。フォーマット・型・試験の実行入口を一本化する。写真、カタログ、トークン、ローカルDBとSDK配布物をGit対象外にする。
- 完了条件：クリーンな環境から固定依存を導入でき、空のアプリに実機成功を偽装する処理がない。SDKとプラグインのライセンス上の出典記録方針がある。実行方法をREADMEへ記載するのは実装済みコマンドに限る。
- 検証：固定依存の再導入、最小パッケージimport、CIの失敗伝達。機能の実機受入とは別に記録する。

### T-01：SDKの成立確認

- 入力：Lightroomが動くMac、採用SDK、テスト用カタログ、権利上使用可能なRAW/JPEGのコピー。出力：G-01〜G-06の証跡、マッピング、支持する環境の一覧。配置：`scripts/probe_sdk/`、`compatibility/`、`docs/validation/`。
- 手順：公式API Referenceで呼び出しと非同期文脈を確認し、1枚の取得、4項目の変更、スナップショット、JPEG生成、復旧を最小コードで実施する。実際のソケット待受範囲と切断動作を調べる。XMP自動書き込み設定と原本ハッシュの変化も別途記録する。
- 完了条件：ゲートごとに環境版、コードコミット、入力形式、API、期待結果、実測結果、対応可否が記録される。RAW/JPEGの値の単位、依存するホワイトバランス項目、許容誤差を表として確定する。
- 検証：V-01、V-02、V-03、V-07、V-17、V-20、V-23、V-26。API不在や環境なしは対応済みにしない。機能が不可能なら代替候補と満たせない要求IDを記録する。

### T-02：ドメイン型とポリシー

- 入力：仕様第4・7・8・12・13章。出力：共通型、スキーマ、正規化と検証処理、共通fixture。配置：`domain.py`、`schemas.py`、`policy.py`、`tests/contract/`。
- 手順：PhotoRef、PhotoState、EditPlan、Operation、Previewを型にする。4項目、絶対値/差分、単位、値域、期限、空対象・重複対象を検査する。SDK未検証の形式は書き込み拒否とする。
- 完了条件：未知キー、非有限数、boolean、数値文字列、単位違い、対象の重複を拒否する。同じ入力から同じ絶対変更値が得られる。M1/M2で型契約を変更しない。
- 検証：V-04、V-05、V-06、V-24。Lua側と同じ入力fixtureを共有する。

### T-03：保存と冪等性

- 入力：仕様第7・9・10章とT-02の型。出力：SQLite migrations、計画の消費、操作・写真別記録、クラッシュ後照合対象の抽出。配置：`store.py`、`migrations/`。
- 手順：操作IDと計画IDの一意制約、親子関係、トランザクション、内容ハッシュを実装する。送信前に`dispatching`を保存し、未完了状態を次回起動で検出する。
- 完了条件：同一ID/同一内容は既存結果、異なる内容は競合になる。別操作IDで同計画を消費できない。DB書き込み失敗時はSDK送信ゼロ。復旧が元履歴を消さない。
- 検証：V-08、V-11、V-12、V-13。プロセス強制終了を含む障害注入で、保存と送信の間を検証する。

### T-04：プラグインとブリッジ

- 入力：仕様第5・6・12章、G-05。出力：Luaライフサイクル、2経路ソケット、認証、単一起動ロック、Pythonクライアント。配置：`bridge.py`、`plugin/LrcMcp.lrplugin/`。
- 手順：専用データ領域・トークンを初期化する。受信処理は検証と直列キューまでに留める。世代ID、nonce、要求IDと期限を確認し、旧応答を捨てる。
- 完了条件：ループバック限定の待受を確認。未認証の命令は処理ゼロ。片側のみ接続、異なるnonce、ポート競合、二重起動、切断で誤成功しない。通常起動時に再インストールしない。
- 検証：V-01、V-02、V-14、V-20、V-24。ローカルTCP模擬試験と実際のLrSocket試験を分離する。

### T-05：写真と現像状態

- 入力：仕様第7章、G-01、G-02。出力：写真ID解決、選択取得、形式別パラメーター、状態トークンと比較。配置：`PhotoAdapter.lua`、`DevelopAdapter.lua`、`State.lua`、`compatibility/`。
- 手順：同名写真・仮想コピー・別カタログを区別する。全選択への暗黙拡大を禁止する。SDK読取設定から競合判定対象を正規化する。計画中の選択変更と現像値変更を別に扱う。
- 完了条件：UIで別写真を選んでも元のPhotoRef以外へ編集しない。未対応形式・プロセス版を明示し、カタログ再起動で古い状態トークンを失効させる。
- 検証：V-03、V-05、V-09、V-10、V-23。

### T-06：プレビュー

- 入力：仕様第8・11章、G-04。出力：SDKレンダリング、PNG等への推測置換をしないJPEG取得、状態照合、比較、キャッシュ管理。配置：`PreviewAdapter.lua`、`previews.py`。
- 手順：変更前後で同じ画像出力条件を使う。GPS/IPTC/不要EXIFを除去する。出力ファイルの所在、形式、サイズを検証する。MCPに画像を返す経路とキャッシュ期限切れを実装する。
- 完了条件：画像が正しい写真と現像状態に対応する。元ファイルのサムネイルを編集後として返さない。キャッシュ外に書かず、期限切れ比較は明示エラー。数値適用の成否と画像取得の成否を分離する。
- 検証：V-07、V-17、V-18、V-25。色と露光の異なるテスト写真で現像反映を比較する。

### T-07：変更の全経路

- 入力：仕様第8・9章、T-03〜T-06、G-03・G-06。出力：計画→prepare→永続保存→apply→読戻しの経路。配置：`service.py`、`jobs.py`、`Operations.lua`。
- 手順：サーバーとLuaの両側で現在状態を確認する。スナップショットの作成と変更前記録の永続化後にだけ適用可能なトークンを発行・消費する。WB等の依存項目も差分に含める。
- 完了条件：保存できなければ現像変更なし。値域、単位、対象、期待状態のいずれかが不正なら拒否する。未知の副作用があれば成功にしない。保存成功の検証とSDK呼び出し間の故障も検出する。
- 検証：V-06、V-08、V-09、V-11、V-12、V-21、V-26。

### T-08：復旧と回復

- 入力：仕様第9・10・13章。出力：`get_operation`、復旧ジョブ、再起動照合、単写真キャンセル。配置：`service.py`、`jobs.py`、`Operations.lua`。
- 手順：元操作の適用後状態を期待値として復旧を計画する。復旧も新操作として保存する。不明操作ではSDKの現在状態と変更前後記録を比較し、勝手に再送しない。
- 完了条件：直前操作を戻せる。後続の手動変更があれば停止する。SDK未完了のまま次の書き込みを開始しない。復旧失敗と状態不明を別の結果として提示する。
- 検証：V-12、V-13、V-15、V-21、V-22。復旧途中のクラッシュと、元操作と異なるカタログでの復旧要求を含む。

### T-09：MCPインターフェース

- 入力：仕様第8章とドメインサービス。出力：ツール一覧、JSON Schema、構造化結果、stdioエントリーポイント。配置：`server.py`、`cli.py`、`tests/integration/`。
- 手順：公式SDKを使用し、各ツールをドメインサービスへ接続する。画像・テキスト結果をホストへ返し、SDK差による通信仕様はSDKで処理する。コード内の生ブリッジ応答をそのままエージェントへ返さない。
- 完了条件：Lightroom停止中もツール一覧と診断を取得できる。stdoutにログが混ざらない。スキーマと実動作の型が一致する。公開されていない任意SDK実行経路がない。
- 検証：V-01、V-04、V-19。MCPクライアントでツール列挙・呼び出し・画像結果・エラーを往復させる。

### T-10：単写真MVPの受入

- 入力：T-01〜T-09、実機、テスト用RAW/JPEG、ローカルMCPクライアント。出力：M1受入記録。
- 手順：1枚を選択→プレビュー→4項目の変更→結果比較→微調整→復旧を実施する。代表的な故障を注入し、元写真以外への変化がないことを確認する。
- 完了条件：V-01〜V-15、V-17〜V-19、V-21〜V-26のうちM1対象がすべて合格。環境差によるskipを合格に算入しない。実機対象の版と非対応条件をREADMEへ反映する。
- 未完了時：M1を`blocked_environment`または`in_progress`として維持し、UI上で「利用可能」と表示しない。

### T-11：バッチ

- 入力：仕様第9・12章、M1。出力：複数写真計画、結果集約、ページング、進捗・キャンセル・期限切れ処理。
- 手順：計画受付後の対象を固定する。写真単位に既存の変更経路を使う。個別競合と全体停止条件を区別し、停止後は未着手分を適用しない。
- 完了条件：100枚以下の指定対象を順次処理できる。成功・失敗・不明の枚数と写真別結果が一致する。途中キャンセル・カタログ切替で範囲が拡大しない。大きな選択を黙って省略しない。
- 検証：V-10、V-12、V-13、V-14、V-16、V-22、V-24。まず3枚で中間失敗を再現し、上限枚数では模擬ブリッジで境界・期限を試す。実機の処理時間を別記録する。

### T-12：エージェントの操作手順

- 入力：仕様第3・12章。出力：ユーザー指示を扱うワークフロー文書、MCP説明文、参考画像と対象を維持する評価シナリオ。配置：`docs/workflows/`、`tests/integration/`。
- 手順：対象取得→画像確認→計画→実行→結果確認を定義する。同設定コピーと雰囲気統一を分け、色温度単位の異なる写真を個別に扱う。最大反復後は現状を提示して終了する。
- 完了条件：固定の試験用判断器で、対象固定・上限回数・同設定/写真別調整の分岐を再現できる。実モデルでは画像を確認したか、指定した見た目に近づいたか、未達を隠さないかを評価する。数値一致を美的成功として報告しない。
- 検証：V-19、V-27。モデル名、指示、実行履歴、参考画像ID、対象ID、試行回数を記録する。見た目の評価は決定的なソフト試験と別欄にする。

### T-13：導入と診断

- 入力：仕様第6・13・15章、M1。出力：導入・状態確認・停止・更新のコマンドと手順、クライアント設定例。
- 手順：専用データ領域とトークンの権限を確定する。既存クライアント設定を破壊しない方法で登録例を生成する。診断は認証値を露出せず、原因を段階別に表示する。
- 完了条件：クリーンなMacで導入して実機接続できる。2回目の起動で再インストール・自動更新しない。ポート競合や無効プラグインを区別できる。アンインストールは利用者が指定した構成物のみを削除し、Lightroom本体・原本・カタログを対象にしない。
- 検証：V-01、V-02、V-20、V-28。既存の他MCP設定を含むfixtureで差分検査。実在する起動パスだけをREADMEへ掲載する。

## 9. 証跡・引き継ぎ・完了の書式
